# CMS development pipeline qualification

The supported development boundary is verified source download, local editing,
review plans and explicitly parameterized create-only scratch upload. Production
replacement and CMS build/test execution are not implemented or enabled.

Live qualification on 2026-10-16 created `ZVF69FE6 EXEC A1`, verified corrected
DFT readback, and independently verified two native reads plus unchanged metadata:
63 F80 records / 5040 bytes, exactly matching the approved candidate SHA-256.
The file remains retained and unexecuted. This closes the corrected create-only
upload qualification gap for the tested fixed-80 ASCII source path. See
`zvm-upload-native-qualified-evidence.json` in local evidence.

## Qualified behavior

- Read-only command captures correlate every record and actual CMS RC with a
  request nonce, checksum, acknowledgements and a fresh wrapper Ready boundary.
- Native downloads verify two identical reads and matching metadata before and
  after. Local snapshots preserve record boundaries, native bytes and hashes.
- Local editing pins the baseline, enforces cp037 and record widths, and emits
  exact candidate/diff/plan hashes. Plans authorize no host write.
- Create-only upload is separately gated, limited to an absent exact
  `ZVxxxxxx EXEC A1` target and requires readback. Existing files are refused.
  Failure after a send warns that a partial host file may exist. No automatic
  overwrite, retry, cleanup or execution follows.
- The optional live validator native check uses the existing verified reader
  for two more reads of the new scratch target and compares the candidate hash.
- A source archive and offline report are generated by `build_zvm_tooling.py`.
  Local builds never connect to CMS or qualify a new production write path.

## Next transaction requires these operator choices

`zvm_operation_plan` now implements this stage as a local review artifact. It
accepts exact edit/plan IDs, the pinned plan SHA-256 and a JSON recipe. It never
connects to CMS and never implements or authorizes replacement/build execution.
An incomplete recipe is valid for review: the manifest lists missing inputs.
`review_complete=true` means required fields were supplied, not that the operator
statements, command semantics or output inventory have been verified.

| Required input | Concrete content |
| --- | --- |
| Production source | Exact filename, filetype and numeric filemode; explicit permission to replace this file |
| Baseline | Fresh native snapshot and metadata; expected SHA-256 and record lengths |
| Candidate | Exact review-plan and native candidate hashes |
| Writer exclusion | Operator-established procedure identifying other writers/sessions, affected disk, owner and validity period |
| Backup/rollback | Verified native backup location and exact restore action/target, including separate restore authority |
| Build recipe | Exact documented compiler/assembler/EXEC invocation and all source/input file IDs |
| Build outputs | Every output file ID, with create/replace policy for each, including temporary and listing files |
| Test recipe | Exact command, expected RC and output assertions; timeout and required final postchecks |

The command and reader helpers are not production-demo replacement targets.
The original protected G generation, A/G disks, MODULEs and rollback sources
remain outside a generic test authorization. Do not choose an existing project
file simply because its source appears in the repository.

## Local recipe contract

The optional recipe keys are `steps`, `input_hashes`, `writer_exclusion` and
`rollback`. The empty object produces an explicitly incomplete review.

Each step must contain all six fields:

- `name`: a distinct simple identifier, at most 32 characters.
- `command`: 1..32 exact printable command tokens. Separators, wildcards,
  quotes, controls and administrative/destructive command verbs are rejected.
  The joined command must fit the known 139-character CMS input field.
  Tokens are retained for review only; their CMS meaning is not verified.
- `inputs`: literal filename/filetype/numeric-filemode strings. At least one
  step must consume the reviewed source. External inputs need explicit hashes
  in `input_hashes`; inputs produced by earlier steps are checked for ordering.
- `outputs`: objects containing exact `file` and `policy: "create_only"`.
  Outputs are restricted to A1 and cannot collide with source, inputs, other
  outputs, helper namespaces or retained scratch namespaces.
- `expected_rc`: a signed 32-bit integer, not a boolean.
- `expect`: bounded printable output markers; absent markers are reported as a
  missing input. Nothing is executed or matched against a host in this stage.

`writer_exclusion` needs `owner`, `procedure`, `evidence_ref` and a `disk`
matching the source's numeric filemode. These are unverified operator statements.
`rollback` needs the exact original `snapshot`, `sha256`, `target` and a
`procedure`. The planner checks the local backup binding; it does not establish
restore authority or qualify a recovery action.

Operation manifests preserve the exact source target derived from the snapshot;
the caller cannot retarget a production source. G/non-A1 sources, helper targets
and retained scratch targets remain explicitly blocked. Every manifest states
`execution_authorized=false`, `execution_implemented=false`,
`replacement_safe=false` and `host_operations_performed=false`.

`validate_zvm_operations.py` exercises the actual MCP tool while disconnected
and independently verifies the manifest hash and its disabled execution gates.
It accepts `--root`, exact `--edit-id`, `--plan-id`, `--plan-sha256`, `--output`,
optional `--recipe-file`, and an optional local `--credential-file` for redaction.

## Proposed implementation gates

Gate 2 now has a local symbolic failure rehearsal in `zvm_rehearsal.py`, with
strict revalidation of the pinned operation review and all source artifacts.
The standalone validator checks twenty scenarios for a two-step synthetic recipe:
one assumed-success path and nineteen exact fail-stop boundaries. It exercises
writer/baseline/backup/input/output preconditions, partial transfer, candidate
readback, each step's dispatch/RC/markers/output checks, and final Ready/inventory.
Every modeled failure retains uncertainty and stops without retry, restore,
cleanup or later-step dispatch. Reports preserve all host authorization blockers.
This supplies an offline specification and regression gate only; there is no
replacement/build adapter under test, and real fault/recovery qualification
remains outstanding. No production transaction choices have been inferred.

1. Resolve the exact transaction above and produce a local review-only operation
   manifest. Refuse unspecified target names, commands, outputs or policies.
2. Validate syntax, widths, input/output collisions, hashes and capability flags
   offline. Model failure before writing, during transfer, after readback and
   during compilation. Prove that each failure stops with retained evidence.
3. Validate backup/replacement/rollback on explicitly authorized disposable
   fixtures before targeting an existing production source. A successful new-file
   upload does not establish replacement safety.
4. Within the established writer exclusion, verify the baseline again immediately
   before replacement. Any change aborts the transaction. A successful
   `CP QUERY LINKS` remains observational; it is not a lock or writer exclusion.
5. Verify native candidate bytes and metadata after replacement before executing
   a build. Transfer completion, keyboard unlock and an old Ready prompt are
   insufficient. Stop on ambiguity; do not issue an automatic restore or retry
   unless the exact recovery action has been separately authorized.
6. Execute only the reviewed fixed build/test recipe, capturing all native output
   and actual CMS return codes. Verify the declared output files and final Ready
   boundary. Archive the complete operation evidence locally.

No replacement, restore, build, cleanup or production input is authorized by this
document. It makes the next implementation and approval scope explicit.
